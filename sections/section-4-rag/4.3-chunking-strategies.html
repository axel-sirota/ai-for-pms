Section 4 - RAG

Chunking Strategies

How you split documents determines whether RAG finds the right information.

Failure Story: The Price Quote Problem

A customer service RAG system kept giving wrong prices. Investigation revealed the problem: the pricing document said "The Pro plan costs $99 per month, which includes unlimited users and priority support."

But the chunking split it as: Chunk 1: "...The Pro plan costs $99 per" - Chunk 2: "month, which includes unlimited..."

The retrieval found Chunk 1 but missed the crucial "per month" - sometimes returning $99 per year based on the model's interpolation.

Lesson: Bad chunking = bad answers. Always test chunking with real queries before launch.

PM Decision Point

Your engineering team will ask: "What chunk size should we use?" The answer depends on:

  • Document type - FAQs chunk differently than legal contracts
  • Query type - Fact lookups need small chunks; analysis needs large
  • Cost tolerance - More chunks = more storage and compute

What Is Chunking?

Chunking splits your documents into smaller pieces that can be embedded and retrieved individually. It's necessary because:

  • Embedding models have token limits (usually 512-8192 tokens)
  • Smaller chunks enable more precise retrieval
  • You only want to send relevant context to the LLM, not entire documents

Chunking Strategies

Fixed-Size Chunking

How: Split every N characters or tokens, regardless of content.

Pros: Simple, predictable chunk sizes

Cons: Splits mid-sentence, loses context

Use when: You need simplicity and your docs are homogeneous.

Sentence-Based

How: Split on sentence boundaries, group N sentences per chunk.

Pros: Preserves complete thoughts

Cons: Variable chunk sizes

Use when: Your docs have clear sentence structure (FAQs, articles).

Paragraph-Based

How: Split on paragraph breaks.

Pros: Preserves topical units

Cons: Paragraphs vary wildly in size

Use when: Your docs are well-structured with clear paragraphs.

Semantic Chunking

How: Use embeddings to detect topic shifts, split at boundaries.

Pros: Best retrieval quality

Cons: More complex, slower indexing

Use when: Quality matters more than indexing speed.

Overlap means chunks share some content at boundaries. This helps when important information spans chunk boundaries.

Overlap % Effect Trade-off
0% No redundancy Risk losing context at boundaries
10-20% Good balance Recommended default
50%+ High redundancy Storage bloat, duplicate retrieval

Chunk Size Guidelines

Document Type Recommended Chunk Size Why
FAQs 1 Q&A pair per chunk Each Q&A is a complete unit
Product docs 200-500 tokens Balance between specificity and context
Legal contracts Clause-based Each clause is a logical unit
Support tickets Entire ticket Context from full conversation matters
Research papers Section-based Preserve argument structure

Stakeholder Framing

When engineering says "We'll use 500-token chunks":

"How did we arrive at 500 tokens? Did we test it against real user queries? Our FAQ answers average 150 words - are we keeping each Q&A together or splitting them? Let's run a quick test with 20 real questions and see if the chunks we retrieve actually contain the answers we need."
